# InclusiveToiletProject 开发路线与改进方向

更新时间：2026-07-10

## 当前判断

项目已经从“依赖后端的数据采集半成品”转向“前端静态数据包 + PWA + 本地采集缓存”的方向。这个方向是合适的：卫生间地图的核心使用场景常发生在路上、弱网、短暂停留时，前端离线能力和快速采集体验比复杂后端更重要。

当前已经具备：

- v6 数据结构、旧数据导入预览和 200 条青岛模拟数据。
- 静态 `manifest.json` + 区域 JSON 的加载流程。
- PWA 应用壳、静态数据和 OSM 瓦片的缓存策略。
- 搜索、条件筛选、最近排序、当前位置显示、导航跳转。
- 新增、编辑、浏览器本地缓存、批量导出本地缓存。
- 地图底图样式切换、移动端筛选浮层、详情抽屉和标签化信息展示。

下一阶段的重点不应该是继续堆字段，而是让“快速采集、静态分发、数据质量、离线可用性”形成闭环。

## 总体目标

1. 采集者在 10-15 秒内保存一条可用草稿。
2. 普通用户打开页面后无感加载所在区域数据，弱网或离线也能查最近厕所。
3. 数据维护者可以导入旧数据、批量校验、人工 review、合并重复点位并导出静态数据包。
4. 项目不依赖自有后端，但保留将来接入同步服务或社区提交系统的接口边界。

## 近期优先级

### P0：快速采集模式

目标：路过时能快速记录，不要求一次填完。

建议实现：

- 新增“快速采集”入口，默认只显示：
  - 使用当前位置
  - 名称或一句话描述
  - 类型标签：男厕、女厕、中立、家庭、无障碍
  - 允许停车
  - 是否开放或备注
  - 保存到浏览器缓存
- 复用上一次采集的国家、省份、城市、进入限制和默认类型。
- 自动生成名称，例如“青岛市 市南区 卫生间草稿 14:23”。
- 支持稍后在数据维护页补全字段。
- 允许拍照或语音备注作为未来扩展，但不要阻塞 10-15 秒采集目标。

验收标准：

- 手机端从打开采集页到保存草稿，常规路径不超过 4 次点击和 1 次文本输入。
- 没有网络时仍能保存草稿。
- 保存后能在数据维护页看到并导出。

### P0：数据质量与 review 工作流

目标：让外部导入、模拟数据、人工采集的数据能被清楚地区分。

建议实现：

- 强化 `audit.reviewed`：
  - 外部导入默认 `false`。
  - 人工新增默认 `true`。
  - 人工编辑可手动设置。
- 增加数据质量状态：
  - `draft`：草稿，仅本地保存。
  - `reviewRequired`：需要人工确认。
  - `verified`：已经人工确认。
  - `deprecated`：停用或过期。
- 在数据维护页增加“待 review”视图。
- 增加重复点位检测：
  - 同名相近。
  - 坐标距离小于阈值。
  - 外部 ID 相同。
- 增加批量操作：标记已 review、停用、导出选中项。

验收标准：

- 外部导入数据不会被误认为人工确认数据。
- 数据维护者可以在一个页面内完成筛选、确认、编辑和导出。

### P0：区域数据分片

目标：用户只下载需要的区域，不一次加载全量数据。

建议实现：

- 扩展 `public/data/manifest.json`：
  - 支持多个区域。
  - 每个区域提供 bbox、版本、记录数、hash、更新时间。
- 首页根据当前位置或地图视口选择区域。
- 增加区域包下载状态：
  - 未下载。
  - 已缓存。
  - 有更新。
- 支持手动下载区域包和清理缓存。

验收标准：

- 首次打开只加载 manifest。
- 获取当前位置后只加载附近区域。
- 已下载区域在离线状态下仍可浏览。

## 中期路线

### P1：静态 ZIP 包与离线缓存

当前 JSON 直接缓存已经能工作，但如果数据和元信息变多，ZIP 包会更适合离线分发。

建议策略：

- 短期继续使用 manifest + JSON，保持简单。
- 当区域数据、索引、图片元数据明显增多时，再引入 ZIP。
- ZIP 包内容建议：
  - `manifest.json`
  - `regions/*.json`
  - `indexes/*.json`
  - `checksums.json`
- 浏览器端解压后保存：
  - 小型 JSON：Cache Storage 或 localStorage。
  - 大型区域包、图片、编辑历史：IndexedDB。

注意点：

- ZIP 解压库会增加 bundle 体积，最好懒加载。
- 需要处理存储配额、下载中断、版本失效和回滚。

### P1：搜索索引与地图性能

现在数据量只有 200 条，直接过滤没有问题。后续数据增长后需要避免一次性渲染和全文遍历。

建议实现：

- 根据地图视口过滤点位，只渲染当前视野附近数据。
- 点位数量较多时启用聚合或分层展示。
- 为名称、地址、类型、进入限制建立轻量搜索索引。
- 搜索和筛选逻辑拆出 composable 或 domain service，避免继续堆在页面组件里。
- 地图点位样式继续保留性别/中立/混合色彩，但需要增加无障碍和待 review 的视觉提示。

验收标准：

- 1 万条记录以内搜索和筛选不卡顿。
- 地图拖动和缩放时不会明显掉帧。

### P1：PWA 更新与缓存管理

当前已经有 PWA 和缓存，但用户还不知道什么时候有新版本。

建议实现：

- 应用启动时检查 manifest 版本。
- 如果静态数据有更新，提示用户刷新数据包。
- 增加设置页：
  - 查看已缓存区域。
  - 清理地图瓦片缓存。
  - 清理本地采集草稿。
  - 显示当前 app/data/mock 版本。
- 增加离线状态提示。

验收标准：

- 用户能清楚知道当前看的数据版本。
- 用户能手动释放缓存空间。

### P1：详情页与列表体验

已有详情抽屉和标签化信息，但还可以继续提升信息层级。

建议实现：

- 详情页顶部固定摘要区：
  - 距离。
  - 是否开放。
  - 无障碍。
  - 是否上锁。
  - 是否允许停车。
- 列表支持紧凑/详细两种密度。
- 在列表中突出最近距离、review 状态和是否启用。
- 移动端底部操作固定，避免滚动到底部才能点击导航。

## 长期路线

### P2：自然语言辅助填写

这个项目可以先做规则解析，不必一开始嵌入大型模型。

建议路线：

- 第一阶段：规则解析。
  - “男厕”“女厕”“无障碍”“能停车”“24小时”“上锁”等关键词映射到字段。
  - 地名和楼层描述写入 `address.description`。
- 第二阶段：轻量本地模型或远端可选模型。
  - 只作为辅助预填，不自动保存。
  - 用户必须确认。
- 第三阶段：语音输入。
  - 浏览器语音转文字后走同一套解析层。

验收标准：

- 输入一句“青岛万象城一楼女厕，有无障碍，能停车，服务台拿钥匙”可以预填主要字段。
- 解析失败不会破坏已有表单值。

### P2：社区提交与同步

虽然当前目标是不依赖后端，但未来可以保留扩展路线。

可选方案：

- GitHub Issues/PR 作为数据提交入口。
- 静态站生成待 review JSON。
- 将来再接入轻量同步服务。

设计原则：

- 前端静态查看和本地采集必须独立可用。
- 云端同步只能是增强能力，不应成为基础依赖。

## 工程改进

### 组件和状态拆分

当前 `LookupPage.vue` 承担了过多职责。建议拆分：

- `ToiletSearchToolbar.vue`
- `ToiletFilterPanel.vue`
- `MobileFilterSheet.vue`
- `ToiletResultList.vue`
- `ToiletDetailDrawer.vue`
- `useToiletFilters.ts`
- `useUserLocation.ts`
- `useToiletNavigation.ts`

收益：

- 页面更容易维护。
- 搜索、定位、详情、筛选可以独立测试。
- 后续桌面端和移动端样式不会互相牵制。

### 类型和校验

当前 v6 类型已经清晰，但校验还比较宽松。

建议实现：

- 校验 `audit.reviewed` 必须是 boolean。
- 校验 `facilities` 只接受已知 key。
- 校验 bbox、经纬度范围、时间戳、opening hours。
- 给导入结果返回 warning，而不仅是 errors。
- 增加 schema fixtures：
  - 最小合法记录。
  - 完整记录。
  - 旧版本导入样例。
  - 错误记录样例。

### 测试与 CI

目前只有构建验证，不足以保护数据迁移和筛选逻辑。

建议增加：

- 单元测试：
  - v6 validation。
  - legacy import。
  - distance sorting。
  - filter matching。
- 构建检查：
  - `pnpm typecheck`
  - `pnpm build`
  - mock 数据生成后 schema 校验。
- E2E 冒烟：
  - 首页加载静态数据。
  - 获取当前位置失败时不崩。
  - 打开详情、编辑、导出。

### 依赖与安全

GitHub 推送时提示默认分支存在 Dependabot 漏洞提醒。建议安排一次依赖治理。

建议步骤：

1. 查看 GitHub Dependabot 报告。
2. 优先处理 high severity。
3. 锁定 Vite、Element Plus、Vue、OpenLayers 的兼容升级范围。
4. 每次升级后运行类型检查、构建和核心手动验收。

### Bundle 体积

当前构建有 chunk 超过 500 kB 的提示。

建议：

- 路由或页面级动态导入。
- 地图、PWA、ZIP 解压、自然语言解析等重功能懒加载。
- 检查 Element Plus 是否需要按需引入。

## 数据结构建议

v6 当前方向可继续保持：

- 地址只保留国家、省份、城市和描述，避免过度结构化。
- 卫生间类型保持简化，蹲厕/坐厕/小便池不进入核心类型。
- `facilities` 继续表达具体设施能力。
- `accessibility` 继续表达无障碍专用信息。
- `audit` 表达来源、更新时间和人工 review。

后续谨慎增加字段：

- 增加前先确认是否会影响 10-15 秒采集。
- 如果只是少数人需要，可以放到备注或扩展字段，不进核心表单。
- 字段必须有“未知”状态，不要强迫采集者现场判断。

## 建议版本路线

### v0.6.x：打磨当前静态前端闭环

- 快速采集模式。
- 数据维护页待 review 视图。
- 区域 manifest 多分片。
- 移动端详情和筛选体验继续打磨。
- v6 validation 加强。

### v0.7.0：离线区域包

- 按区域下载和缓存。
- 缓存管理 UI。
- 数据版本更新提示。
- 可选 ZIP 包导入。

### v0.8.0：批量维护与迁移

- 旧版本数据迁移工具。
- 批量 review、合并重复、停用。
- 导出静态站数据包。
- 引入测试覆盖迁移逻辑。

### v0.9.0：辅助采集

- 自然语言预填。
- 可选语音输入。
- 图片/备注草稿。
- 快速采集统计和质量提示。

### v1.0.0：稳定静态发布

- 数据结构冻结。
- 静态数据包规范稳定。
- PWA 离线体验稳定。
- 文档齐全，允许社区按规范贡献数据。

## 下一步建议

最建议先做两件事：

1. 快速采集模式。
2. 数据维护页的待 review 工作流。

这两件事能直接解决当前项目最核心的问题：数据如何高效产生，以及产生后如何变成可信的静态数据包。
